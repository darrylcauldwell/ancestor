# CROSS_PROFILE_CORROBORATION_SPEC — spouse-pair marriage corroboration across profiles

**Status: Changes 1–4 SHIPPED 2026-07-26** (`f1adb88` corroborator · `3434fc9` sweep — live-verified on the Mary Ellen Thompson × William Holmes demonstrator, cards accepted, edge written, leads resolved · `ae53bf9` in-run annotation · `6fb81c6` verdict elevation + §4.2 amendment). **Change 5 DEFERRED (owner decision 2026-07-26): the machine-commit carve-out waits for the §14.B.2–6 transaction/undo keystone, extended to relationship entities — or for corroboration volume that makes the two-click human path a real cost.** Rationale: §14.2 principle 5 (false auto-approvals are the failure mode; missed ones are throughput loss), the unbuilt §14.B.4 undo, and the §1 couple-namesake residue that only a human eyeball on the card catches today. Change 5's design below remains the build plan when its gate opens. Drafted 2026-07-26 from a 9-subsystem code-verified seam map; revised same day after a 4-lens adversarial review (21 findings folded, see footer).

**Governing invariants:**

- **(a) Exact-tuple determinism.** The join is canonicalised reference-tuple equality plus a deterministic guard ladder. No AI anywhere in detection, grading, or elevation — this extends the deterministic sandwich, it does not perforate it.
- **(b) No ad-hoc verdict mutation.** `evidence_records.verdict` is scorer-owned and re-stomped on every run (`ProjectDatabase.swift:3544-3598` — only `user_status` survives). Corroboration therefore lands either as a **fact proposal through the firewall** (pending_facts → review → edge write) or as a **scorer input recomputed every run** (Changes 3–4). Nothing ever UPDATEs a stored verdict directly.
- **(c) Fail closed, refuse ambiguity — but never mistake duplication for ambiguity.** `referenceKey` returns nil without vol+page (`SamePageCouplePairing.swift:29-37`) — preserved. A spouse pair with ≥2 distinct shared keys, a key claimed by ≥2 edges anywhere in the sweep pass, or a same-key collision with **conflicting** partner identities emits **nothing**. Identical duplicates (re-fetches, multiple volunteer transcriptions of one index line) are collapsed, not treated as ambiguity — see Decision 13.
- **(d) Human in the loop until the final change.** Changes 1–4 end in pending_facts/human review or in a verdict that still requires the existing accept flow to write anything. Change 5 is default-OFF behind its **own** env flag, and is an explicit, written **amendment to §14.B.7** — the governing text (`RESEARCH_PIPELINE_SPEC.md:1187-1191`) currently excludes *"auto-approving relationships, life events, or attachments"* wholesale, with no scalar-field carve-out; Change 5 adds that carve-out to the governing spec (scalar marriage fields on an existing edge, fill-nil-only), leaving relationship-row creation/deletion excluded as before.
- **(e) E5 no-self-confirmation, strengthened to person-identity.** A corroboration is elevation-grade only via linkage back to the subject **and** a non-vacuous anchor: the tree spouse edge, both subjects independently holding a same-key record, and at least one party whose own dated facts actually test the marriage year (§1 anchor model). Record-pair unity alone is never sufficient for machine elevation.

**What this is:** the first cross-profile join in the engine. Today every stage is subject-centric — `RecordScorer.classify` sees only (record, subject); `ConvergenceEngine` is subject-blind; no orchestration layer (whole-tree loop, watcher, ConflictSweep, CampaignReview) ever reads two profiles' results together (verified 2026-07-26). Yet two tree-linked spouses each independently hold a FreeBMD marriage-index lead citing the same GRO reference — the demonstrator: Mary Ellen Thompson (name-only facts, ~500 namesake leads) × William Holmes (d. 1919), both holding **Dec 1915, Bakewell, 7b/2130a**, triangulated by son Reginald b. 21 Jul 1916. Each sits at `.lead` because neither subject's *own* facts converge; the pair, the edge, and the anchors together are decisive. This spec assembles that evidence chain deterministically: a post-run **CorroborationSweep** over spouse edges (Changes 1–2, works on already-persisted data), an **in-run annotation + bounded verdict rule** so elevation is reproduced by the scorer itself on every run (Changes 3–4, a §4.2 doctrine amendment), and a **§14 carve-out** for machine commit (Change 5, last, gated, itself a §14.3.2/§4.3/§14.B.7 amendment).

**What this is not — the G1 boundary, stated on G1's full text.** §16.1's G1 says a re-research of a relative *"refetches the shared marriage record and treats it as a fresh hit instead of recognising it"*, and notes *"ConvergenceEngine operates per-cluster, never across clusters that span profiles"* (`RESEARCH_PIPELINE_SPEC.md:1255-1259`); Part II gates G1 on Decision 7.9 because cross-profile dedup *"needs cluster-aware match strength to know when two clusters across profiles describe the same person"* (`:2346-2351`). This spec does recognise a relative's copy of the shared record — but it answers the person-identity question 7.9 exists for by **different, stronger means**: exact-tuple record identity (canonicalised GRO reference), the tree spouse edge as the person prior, and the §1 anchor requirement (a party's own dated facts must test the marriage year) before any elevation. Fetch-economy dedup, cluster-aware match strength, and cross-profile convergence arithmetic remain G1/7.9 territory, untouched and still open; G1 should reuse Change 1's joiner when built. Not a general family-evidence framework — spouse-pair marriage records only (Non-goal 8).

## 1. The correctness model — what a shared GRO reference actually proves

Two distinct questions, which the original 2026-07-25 framing ("same vol/page = definitionally one marriage") conflated — and the code already knows better: `WitnessIdentity` keeps `surnameNorm`/`givenInitial` in the witness key precisely because *"a GRO vol/page identifies an index PAGE holding 2–4 entries, not a single line"* (`WitnessIdentity.swift:19-46`).

**Question 1 — record-pair unity: are the two records two sides of ONE registered marriage?**

- **Reciprocal (from the March quarter of 1912).** Both index entries carry the spouse-surname column (year-granularity constant `ScoringRules.spouseSurnameStart = 1912`, `ScoringRules.swift:139`; tier assignment is purely **column-presence-based**, never date-based). Require **reciprocal agreement**: each side's spouse column ≈ the other party's surname *set* (nameSimilarity ≥ 0.7). The demonstrator (Dec 1915) is reciprocal.
- **Same-page-prior (column absent on either side).** Same key + the tree spouse edge as prior + partner-surname evidence where available (`partnerSurnameFromSamePage`) — the same epistemic move the shipped within-run machinery already makes (*"the reference tuple does the real identification"*, `MarriageEnrichmentEngine.swift:105-116`), now with the edge as the linking prior. A **present-but-contradicting** spouse column is a contradiction, not a missing column — it refuses, never degrades to same-page-prior. Same-page-prior findings are human-review-only, permanently (Non-goal 7).

**Surname sets, not single surnames.** Marriage indexes file a bride under her **pre-marriage** surname, but this tree frequently stores wives under married surname (documented convention; the shipped married-surname machinery exists for this reason). Each `PairMember` therefore carries a surname *set* — recorded surname plus derived maiden surname(s) via the existing derivation (`ResearchSubject.swift:723-770` pattern) — and every surname comparison in the guard ladder tests against the set. Honest cap: a married-surname-stored wife's *own* bride-side record may have been scored `.impossible` at the name gate upstream (maiden-axis acceptance needs a linked father, `RecordScorer.swift:172-181`) and is then invisible to the corroborator; the surname set fixes the reciprocity test, not upstream visibility.

**Question 2 — couple identity: is that marriage THIS couple's?** Record-pair unity does not answer this. For a doubly-thin pair (both parties name-only), both sides' runs fetch broad surname windows, so both sides of **every** Thompson×Holmes marriage in the fetched window are held by construction — reciprocity is then satisfied vacuously, "exactly one shared key" measures surname-pair frequency in a possibly-truncated fetch corpus, and a sibling double-wedding (two couples with reciprocal surname pairs on one register page) defeats even reciprocal agreement. The **anchor model** answers Question 2:

- **Strong anchor:** at least one party's own date gate passes against the record (a real birth window validating marriage age), OR a linked child's birth-registration MMN matches the corroborated maiden surname with the birth in a plausible window after the marriage quarter (the `childEvidenceMMNLookup` machinery, `ResearchPipeline.swift:92-106`, is the existing read path). Reginald b. Jul 1916 with MMN *Thompson* would be a strong anchor for the demonstrator.
- **Weak anchor:** a party's death year that the marriage year actually precedes (William d. 1919 vs Dec 1915 — a real constraint, but it excludes only post-1919 rivals).
- **No anchor:** neither party's dated facts test the marriage year at all.

**Routing:** the **sweep emits for any tier/anchor combination** — the review card states both honestly (*"reciprocal columns; weak anchor: William's death 1919"*) and the human judges. **Change 4 verdict elevation and Change 5 machine commit require reciprocal + strong anchor.** The residual risk class — a same-surname-pair *couple namesake* whose marriage also fits every anchor — is stated here deliberately: it is small once a strong anchor binds, it is exactly what the human-review card is for in the anchorless case, and no guard in this spec claims to eliminate it. "Conclusive" does not appear in this spec's vocabulary.

**Witness doctrine (DS-03 compatibility).** The two spouses' entries are two index rows for one register event — under `WitnessIdentity.sameWitness` they are *different witnesses* (surnames differ) of *one lineage* (both FreeBMD). Pooling both into `ConvergenceEngine.score` caps at `.possible` (one lineage, `ConvergenceEngine.swift:46`) and levels never touch verdicts anyway. The elevation is a **verdict/proposal-layer structural rule** — the doctrine §14.3.4 already pinned for the within-run case: *"the BMD reference-tuple match IS the structural convergence check"* (`MCPServer.swift:3049-3070`). The §8 convergence ladder is untouched by this spec.

**What elevation yields — honestly.** The marriage fact (registration-quarter-derived date span, district) lands on the spouse **edge**; both leads resolve; maiden-surname/district anchors firm up. It does **not** mint a birth year — Mary's ~500 namesake pool collapses only when a later age-carrying record lands; the existing re-run loop handles that organically (no retro-filter is built or needed). The date span honours registration semantics: GRO quarterly indexes include late clergy returns, so `earliest` is widened by one quarter and the citation reads *"registered Dec quarter 1915, Bakewell"* — the epistemic status travels with the value.

## 2. Decision log

1. **Sweep before scorer.** The persisted-pair case (both runs already done — the demonstrator today) needs zero pipeline changes and zero doctrine changes; it ships first and proves the join live. The in-run path exists for one reason the sweep can't deliver: making the **verdict itself** `.fact` durably (re-stomp-proof, because the scorer reproduces it each run) so convergence/GPS/absorption/cluster-accept all follow automatically.
2. **One key module, two strictness levels — reused, never re-minted.** Two reference-key implementations exist today (`SamePageCouplePairing.referenceKey:29-37` — canonical, tested; a private duplicate at `MarriageEnrichmentEngine.swift:189-196`); the MCP payload merely surfaces the raw tuple fields (`MCPServer.swift:2167-2179`). Change 1 adds `canonicalReferenceKey` to `SamePageCouplePairing`: district canonicalised through `FreeBMDDistrictCatalogue` (exists, currently unused for this) and volume/page zero-stripped à la `WitnessIdentity.norm` (`WitnessIdentity.swift:66-72`) — because the two sides of one marriage are transcribed **independently** (bride-batch vs groom-batch) and FreeBMD district strings are transcriber-variant ("Chapel le F." observed in the wild, `FreeBMDSource.swift:861-869`); verbatim-uppercase equality across batches silently false-negatives. The corroborator joins on the canonical form; the shipped same-page annotate keeps its existing key (both its sides come from one fetch session). A **near-miss diagnostic** (same canonical year|vol|page, district nil-or-similar on one side) is surfaced in the sweep summary — observable, never auto-joined.
3. **The pure-joiner / I-O-orchestration split is inherited.** `SamePageCouplePairing` (pure) + `annotateMarriagesWithSamePagePartner` (I/O) is the in-repo template (`SamePageCouplePairing.swift:10-13`). Change 1's `SpousePairCorroborator` is pure and fully unit-testable; Change 2's sweep and Change 3's pipeline step are its I/O halves.
4. **Cross-profile reads ride the injected-closure precedent.** `childEvidenceMMNLookup` (`ResearchPipeline.swift:25`, factory `:92-106`, wired `ResearchRunService.swift:40`) already reads a relative's persisted evidence mid-run. Change 3 adds the sibling closure `spouseEvidenceLookup` — same shape, same wiring point, graders/scorer stay pure.
5. **Elevation routes through the edge, not profile columns.** A marriage "fact" in this app is data on the spouse relationship edge (`ResearchRunFactBridge.swift:22-24`). The write API exists and enforces Check-Before-Overwrite (`fillRelationshipMarriage`, `ProjectDatabase.swift:2413-2469`, narrower-span-only). Missing plumbing this spec adds: the **pending-fact marriage apply mapping** (`applyAcceptedPendingFact` has no marriage routing and silently no-ops, `ProjectDatabase+PendingFactsReview.swift:47-55`) — Change 2 for the human path, Change 5 for the MCP commit path. `marriageDate`/`marriageLocation` are *already* in `autoApprovableFields` (`MCPServer.swift:2681-2686`); only the plumbing is absent.
6. **One pending-fact pair per spouse edge; machine-readable payload, not citation parsing.** Owner = the pair member whose profile id sorts first (stable, documented on the card, which names both spouses). The routing data — edge id, partner profile id, both evidence-record ids, tier, anchor — rides `pending_facts.sources_json` (the column exists and is written as `'{}'` today, `ProjectDatabase.swift:3870-3882`); the apply path reads it, never parses display text. Two rows per finding: `marriageDate`, `marriageLocation`. `EvidenceFirewall.idempotencyKey` dedups re-sweeps.
7. **Rejection memory at three layers, all honoured.** (i) either side's lead dismissed → the pair never emits again (`Lead.swift:110-124` is the durable channel); (ii) either evidence row `user_status = discarded` → excluded (ConflictSweep precedent, `ConflictSweep.swift:137-138`); (iii) a rejected pending fact is not re-emitted (idempotency key + `review_status`).
8. **Dispute refusal (CL6 parity), both members.** An open `spouseIdentity`/`timeline` dispute on **either** profile, or an open `fieldValue` dispute on the edge's marriage fields, refuses emission. Change 5 must extend the MCP evaluator to match: the shipped CL6 check queries only the fact's single profile id (`MCPServer.swift:2983-2991`), which under the owner rule would miss a dispute on the non-owner spouse — the carve-out's evaluator reads the partner id from the payload and checks both.
9. **Conflicting edge data → skip, never dispute-mint.** Existing edge date conflicting (non-overlapping spans) → the sweep emits nothing; the conflict layer owns dispute creation (no new dispute producers). Equal-or-narrower existing data → nothing to gain → skip, logged in the sweep summary.
10. **The verdict rule is narrow by enumeration (Change 4).** Elevation fires only when: (i) the record carries a **reciprocal-tier, strong-anchor** cross-profile annotation (tier and anchor are recorded in the annotation — the gate-4 pass may come from any arm, see Decision 15); (ii) name and geography both passed with zero softFails; (iii) the only blocker is the insufficient-information date fail (`RecordScorer.swift:538-540`, which gains a dedicated distinguishable reason) or the thin-subject cap (`:112-116`, which gains the matching exemption); (iv) date `.impossible` and every other configuration are untouched. Contradiction-shaped failures are never overridden. Precedent for post-gate verdict adjustment: the mode-dependent geography mapping (`:99-100`) and the thin cap itself.
11. **Key-claim discipline is sweep-wide.** Corroboration is computed per spouse edge, and the sweep keeps a per-pass **key→edge claim ledger**: a canonical key matched by ≥2 distinct edges anywhere in the project (two edges of one profile, duplicate-couple GEDCOM debris, sibling double-weddings) refuses **all** claimants (`.ambiguous`). In-run (Change 3), the ambiguity corpus is stated explicitly: the current batch plus the subject's persisted evidence plus the partner's persisted evidence — so the guard is surface-independent.
12. **Deterministic year-sanity guards, correctly attributed.** Record year ≤ each party's death year where known (margin **0** — marriages are indexed in the ceremony's quarter; `postDeathMarginYears` exists for *lagging* record classes and is deliberately NOT reused here); record year ≥ birth year + `minMarriageAge` where known (a **new** named constant, 14 — the pre-1929 legal minimum; deliberately below the scorer's `ScoringRules.checkMarriageAge` 16 because a refusal guard must not manufacture false negatives on legal Victorian marriages); record year ≤ birth year + `maxAdultAgeYears` (the constant already documented for marriage, `IdentityConstraints.swift:27-29`, currently unused for it).
13. **Duplication is collapsed before ambiguity is judged (repairing, not regressing, the shipped path).** The shipped `annotate` feeds spouse-side entries from two paths with no cross-path dedup (`ResearchPipeline.swift:2442-2459`, `:2480-2502`), so identical duplicates at one key are the **normal** case; FreeBMD also holds multiple volunteer transcriptions of one line under distinct row ids. Change 1's collision handling therefore: dedup by record id → collapse same-key entries whose (surname, givenName) agree → drop the key **only** when surviving entries carry conflicting partner identities. Applied to both the corroborator and the shipped `annotate` (whose current last-write-wins becomes the collapse; behaviour preserved for the benign case, tightened only for true conflicts).
14. **The pending-fact processor must not damage the fact (Change 2 scopes it).** Every reviewed fact runs through `PendingFactsProcessor` (`PendingFactsReviewView.swift:355-360`), which live-fetches the cited URL (auto-reject on failure/mismatch — and a live programmatic FreeBMD fetch per review load is a ToS exposure) and re-scores marriage facts through a synthetic record **stripped of the tuple** (`PendingFactsProcessor.swift:80-104`, `:189-195`). Corroboration facts derive from already-scored, already-cited persisted evidence rows: Change 2 exempts `agent_id = 'cross-profile-corroboration'` from Step-2 URL verification and Step-4 re-scoring, with provenance = the two evidence-record ids in the payload. (The processor also ignores stored `verification_status` — hardcodes `.pending`, `PendingFactsProcessor.swift:59` — which silently defeats the consensus detector's pre-verified escape hatch, `BirthYearConsensusDetector.swift:47-53`; Change 2 fixes that by honouring `verification_status = 'verified'`, which is the general mechanism the exemption rides.)
15. **Gate-4 arm ordering is left alone; the annotation is the signal.** For the demonstrator class the existing spouse-surname arm passes **first** (`RecordScorer.swift:1200-1211`) and the new cross-profile arm would be unreachable — so Change 4's condition keys on **annotation presence** (tier + anchor fields), not on which arm produced the gate-4 pass. The new arm exists only for records where no earlier arm fired (e.g. spouse column absent); no existing arm is re-ordered, no existing reason string re-baselined.
16. **Retraction is a first-class arm, not an afterthought.** Elevation's justification can be withdrawn later (partner's evidence row discarded, partner's lead dismissed, edge deleted). The sweep gains a **staleness arm**: a persisted corroboration annotation (or an un-accepted pending fact) whose partner-side record is now excluded → the pending fact is withdrawn (pre-accept) or a visible *stale corroboration — re-run subject* review item is raised (post-elevation; the next run's annotation step, which recomputes exclusions, then drops the elevation). Deterministic, visible, no hidden writes.
17. **Ordering/fixpoint contract stated.** A subject's verdict becomes a deterministic function of *(subject facts, spouse's persisted evidence state)* — same DB state, same output, but whole-tree **run order** now matters transiently (Mary-before-William yields `.lead`; after, `.fact`). The contract: cross-profile state converges via the existing re-run loop plus the Change-2 post-persist sweep trigger (which fires when the second spouse's run lands and surfaces the pair for action); nothing hidden re-runs a subject. Change 4 carries a run-order-inverted acceptance criterion.
18. **Machine commit is fill-nil-only, single-profile-shaped, and separately flagged.** Change 5's commit: refuses when either target edge column is non-empty (recovery-not-correction — the §5.14 bound, `RESEARCH_PIPELINE_SPEC.md:2096-2098`; strictly tighter than the human path's narrower-span policy), writes the same transaction row the app-side write path records, **never touches lead rows** (lead resolution is the app-side sweep's tidy arm when it next observes the landed fact — machine commits touching a second profile's rows have no precedent and no undo story), and sits behind a **dedicated** env flag (`ANCESTOR_MCP_AUTO_APPROVE_CROSS_PROFILE`, required *in addition to* the base flag) so enabling the shipped §5.14 firstName recovery never silently enables edge writes (§14.2 principle 3: the user can narrow scope).

## 3. Conceptual model

```
PairMember          = (profileID, surnames: Set<String>,      // recorded + derived maiden
                       birthYearRange?, deathYear?)

CorroborationFinding = (edgeID, subjectProfileID, partnerProfileID,
                        canonicalKey, tier: .reciprocal | .samePagePrior,
                        anchor: .strong(kind) | .weak(kind) | .none,
                        subjectRecordID, partnerRecordID,
                        proposedDate: (earliest, latest),     // quarter span, earliest widened
                        proposedLocation: String?,            // canonical district
                        trace: [String])                      // guard-by-guard reasoning

SpousePairCorroborator.corroborate(
    subjectMarriages: [(id: String, record: MarriageRecord)],   // PRE- or post-verdict — caller supplies
    partnerMarriages: [(id: String, record: MarriageRecord)],   // the corpus and the exclusions
    subject: PairMember, partner: PairMember,
    edgeID: String,
    exclusions: CorroborationExclusions        // dismissed leads, discarded evidence, open disputes —
) -> CorroborationOutcome                      // resolved by the I/O half, passed in as data

CorroborationOutcome = .found(CorroborationFinding)
                     | .none(reason)                            // incl. near-miss diagnostics
                     | .ambiguous(reason)                       // TERMINAL for the pass — never degraded
```

The corroborator takes **plain marriage records + ids**, not `ScoredRecord` — the sweep maps its verdict-filtered (`!= .impossible`) persisted rows down; the in-run path feeds the current unscored batch plus both sides' persisted evidence (Decision 11's stated corpus). Pure: no DB, no wire, no model.

Detection surfaces (both call the same corroborator):

```
Change 2   CorroborationSweep (project open + post-persist + manual; ConflictSweep shape)
           spouse edges → both ends' evidence_records → corroborate (+ key→edge ledger)
           → .found → pending_facts (owner + payload, Decision 6) → PendingFactsProcessor
           (exempt, Decision 14) → human review → accept → fillRelationshipMarriage(edge)
           + both leads resolved            + staleness arm (Decision 16)

Change 3–4 in-run: spouseEvidenceLookup closure → pre-scoring annotation on the candidate
           MarriageRecord (tier + anchor + partner ids) → gate-4 pass (any arm) →
           Decision-10 verdict rule → .fact reproduced every run
```

## 5. Changes

Each independently shippable; gate is `xcodebuild test` (serial scheme). Ordering is load-bearing: pure joiner → sweep (value on existing data) → annotation (additive) → doctrine change → auto path.

### Change 1 — pure corroborator + canonical key + same-page collision repair (M)

**Scope:** `SpousePairCorroborator` (guard ladder: tier assignment, anchor assessment, unique-shared-canonical-key, Decision-13 collapse-then-conflict, Decision-12 year guards with the two new named constants, surname sets); `canonicalReferenceKey` + near-miss classification; the Decision-13 repair to `SamePageCouplePairing.annotate`.

**Acceptance criteria:** (1) demonstrator fixture (reciprocal columns, weak anchor from William's d.1919) → `.found`, tier `.reciprocal`, anchor `.weak`, date span widened one quarter, canonical district; (2) demonstrator + Reginald-MMN fixture → anchor `.strong`; (3) doubly-thin no-anchor fixture → `.found` with anchor `.none` (sweep-emittable, never elevation-grade); (4) one side's spouse column absent → `.samePagePrior`; present-but-contradicting → `.none`; (5) page-mate fixture (same key, each side naming a third party) → `.none`; (6) two distinct shared keys → `.ambiguous`; (7) collision triptych: identical duplicate entries → collapsed and matched; same line under two transcription row-ids → collapsed and matched; conflicting partner identities at one key → key dropped (both in the corroborator and in the repaired `annotate`, which keeps annotating the benign cases — regression fixtures from the shipped `SamePageCoupleTests` corpus stay green); (8) district drift fixture ("BAKEWELL" vs "Bakewell " vs catalogue-variant) → joined via canonical key; district conflict → near-miss, not a join; (9) married-surname-stored wife (surname set carries derived maiden) → `.found`; (10) year guards: marriage after a party's death year → `.none`; before birth+14 → `.none`; a legal age-15 Victorian marriage → NOT refused; after birth+`maxAdultAgeYears` → `.none`; (11) pure — no DB/wire in the corroborator's compilation unit.

## 6. Non-goals (explicit)

1. **No new dispute producers** — conflicting edge data skips (Decision 9); the conflict layer owns disputes.
2. **No convergence-ladder or §8 change** — lineage arithmetic, witness collapse, and the pinned thresholds are untouched; the elevation is verdict/proposal-layer. (The one pinned value that DOES move — §14.3.2's lineage minimum, for this agent only — moves via Change 5's written amendment, not silently.)
3. **No stored-verdict UPDATEs** — invariant (b); the only verdict that changes is one the scorer recomputes itself.
4. **No machine relationship-row creation/deletion** — Change 5 amends §14.B.7 for scalar fields on an *existing* edge, fill-nil-only; row-level structure stays human-only.
5. **No leads-table schema change** — the GRO reference stays in `record_json`; the `lead_<recordID>` join (`Lead.swift:172-192`) is sufficient.
6. **No MCP-side join tooling** — an external agent can already do the join manually via two `get_scored_records` calls (`MCPServer.swift:2167-2179`); a server-side join tool would require promoting the key logic to AncestorKit (deferred — Appendix B5).
7. **No same-page-prior or non-strong-anchor auto-approval, ever** — by construction, not configuration.
8. **No generalisation in this spec** — child-birth-brackets-marriage inference, parent-death corroboration, census-household joins are future candidates that must each argue their own correctness model (this spec's §1 shows the shape: record-identity question + person-identity question + anchor).
9. **No retro-filtering of namesake leads** — elevation does not mint a birth year (§1); the existing re-run loop owns pool collapse.
10. **No truncation-aware corpus guard** — evidence rows do not record whether their originating fetch window was truncated, so the unique-key test runs over what was persisted; this residual (§1, couple-namesake class) is mitigated by the anchor requirement and stated on the review card, not silently absorbed.
11. **No Python parity** — the Python agent has no cross-profile machinery, no evidence persistence, no edges-with-marriage-data. Swift-first, Swift-only.
