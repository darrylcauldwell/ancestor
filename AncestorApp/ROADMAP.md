## Near-term fixes

- **BUG (near-term): Add-Relationship anchor "Change" is inert — blocks the disconnected-tree join.** In `Views/ManualEntry/AddRelationshipView.swift`, the "This person" anchor row binds `ProfilePickerField` through a hand-rolled `Binding<String?>` whose setter drops `nil` (`set: { if let id = $0 { anchorID = id } }`, ~line 110), and the backing `anchorID` is a non-optional `String` (~line 22). `ProfilePickerField`'s "Change" reveals its search field by writing `selectedID = nil` (`ProfilePickerField.swift` ~line 36) — but the anchor's setter swallows that nil, so the picker never flips to "Search existing people…" and Change appears to do nothing. "Other person" works only because it binds a real `String?` (`$targetID`). **Severity is more than cosmetic:** the "Connect them?" disconnected-tree banner opens this sheet with a *pre-picked* anchor (smallest component's first profile via `GraphConnectivity.suggestConnectionAnchors`); when that isn't the profile the user wants to bridge from, the dead Change button leaves them unable to retarget — so bridging two disconnected groups via the banner is effectively blocked (observed 2026-07-27 trying to re-parent Samuel Wheeldon to Ruth across two groups). This regresses the deliberately-added "anchor is ALWAYS changeable" safety affordance (doc comment ~lines 18-21; commit `6ae7075`, added after the 2026-07-15 incident where a hidden anchor nearly welded two unrelated families). **Fix:** let the anchor hold nil — either make `anchorID: String?` and pass `$anchorID` directly (guarding the `save()`/`edgeDescription` paths that subscript `snapshot.profiles[anchorID]` for the transient nil), or add a local `@State anchorSelection: String?` bound to the field and written back to `anchorID` only when non-nil. **Workaround (no fix needed to proceed):** launch Add-Relationship from the intended anchor person's own node/card and use the working "Other person" search to reach across groups — never relies on Change. **Status: FIXED 2026-07-27** — anchor now binds a local `@State anchorSelection: String?` synced back into `anchorID` via `.onChange`, so Change reveals the search field; Add is gated on `anchorSelection != nil`. Code applied, app builds green; awaiting in-app behavioural verify + commit.

- **BUG (near-term, DATA-INTEGRITY — HIGH priority): editing a sibling-shortcut placeholder into a real person leaves it auto-retirement-eligible → silent soft-delete + relationship loss.** The sibling shortcut (`AddRelationshipView.siblingShortcut`, `.placeholder` case ~line 432) creates a shared parent with `attributes.nameStatus == .placeholder`. When the user later edits that node into a real person (name + dates), the profile-edit path **does not clear `nameStatus`**. The placeholder-retirement machinery — `AppState.reconcilePlaceholderParent` (called from `save()` case `.parent`) and the excess-parent-edges repair (`PlaceholderParentRepair` / `repairExcessPlaceholderParents`) — then treats the still-flagged node as a disposable stub: **soft-deletes it (`softDeleteProfiles`, `is_deleted = 1`) and removes its parent edges.** The now-real person disappears from the app (its `buildSnapshot` filters `is_deleted = 0`) and its children are orphaned ("Unknown parents"). **Repro 2026-07-27:** Ruth Wheeldon b.1824 (`B4D9B84C`), created by editing the Mary↔Samuel sibling placeholder into a real Ruth, was soft-deleted with all her edges (Ruth→Mary/Kezia/Sarah Ann) stripped; freshly-created siblings Kezia/Sarah Ann (never placeholders) survived. Confirmed `is_deleted = 1` by MCP-vs-app divergence: her row is present (MCP `get_profile` returns her) yet the app excludes her. **Fix direction:** (a) clear `nameStatus` (→ `.normal`) when a placeholder is given a real identity in the edit path; and/or (b) placeholder-retirement must refuse to retire any node carrying real identifying data (non-empty name or any birth/death date), regardless of the flag. **Recovery for already-affected data:** in-app *Restore* alone is NOT durable — a restored profile keeps its `.placeholder` flag and is re-culled on the next relationship op; recreate as a fresh profile (not via placeholder) and re-link, or restore from the auto-backup. **Status: FIXED 2026-07-27** — implemented fix direction (b): `Profile.isAnonymousStub` no longer treats a `.placeholder`-flagged profile that carries a real name/dates as junk, and `AppState.reconcilePlaceholderParent` now retires only `nameStatus == .placeholder && isAnonymousStub` (still-blank) parents. Because (b) is data-independent it also **self-heals already-affected records** (a restored Ruth now survives). Regression tests added (`PlaceholderReconciliationTests.namedPlaceholderSurvivesSecondParent`, `…isAnonymousStubIgnoresFlagWhenRealDataPresent`); PlaceholderReconciliation + AuditEngine suites green (67 tests). Awaiting in-app live verify (restore Ruth b.1824 → she survives adding John) + commit. Fix direction (a), clearing the stale flag on edit, is optional hygiene — not needed now that (b) self-heals. Consistency follow-ups (not cull paths, left as-is): `PlaceholderResolver` and `AuditEngine.swift:75` still key off the raw `.placeholder` flag.

- **BUG (near-term, MCP consistency — LOW risk): `get_profile` and `search_profiles` return soft-deleted profiles.** `MCPServer.profileDetail(id:)` (`SELECT * FROM profiles WHERE id = ?`, ~line 785) and `searchProfiles` (`… WHERE first_name LIKE ? OR last_name LIKE ?`, ~line 929) omit the `is_deleted = 0` filter that the app's `buildSnapshot` and other MCP queries apply (e.g. `MCPServer.swift` lines 1326, 1643, 1837). So a soft-deleted profile is invisible in the app but still surfaced by MCP `get_profile`/`search_profiles` — which sent a long false-trail on 2026-07-27 (looked like a load/persistence bug when the profile was simply soft-deleted). **Fix:** add `AND is_deleted = 0` to both queries (or an explicit `include_deleted` flag for admin/triage). Small, self-contained. **Status: FIXED 2026-07-27** — `AND is_deleted = 0` added to both `profileDetail` and `searchProfiles` (parenthesising the search's `OR` for correct precedence); MCP now hides soft-deleted rows like the app does. Pending MCP rebuild + `/mcp` reconnect to take effect in-session.
